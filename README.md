# AI First

> ИИ-аудитор организационных изменений команды **AI First** для хакатона **hackalem.ai 2026**.

## О проекте

Проект разрабатывается в специальном треке **«Казахтелеком»** и решает задачу
**«Анализ организационной структуры и функционала»**.

При реорганизации положения о подразделениях и организационные структуры обычно
сверяют вручную. Из-за объёма документов отдельные функции могут потеряться,
задублироваться или незаметно перейти между подразделениями. AI First сравнивает
комплекты документов «до» и «после», классифицирует изменения и формирует
проверяемое заключение со ссылками на конкретные пункты исходных документов.

**Ценность:** специалист получает предварительную карту рисков реорганизации и
ссылки для проверки. Экономия времени пока не измерена на работе реального заказчика.

## MVP (в разработке)

- загрузка двух комплектов документов: «до» и «после» реорганизации;
- извлечение подразделений, функций и ссылок на пункты документов;
- сопоставление семантически эквивалентных функций;
- выявление потерянных, добавленных, перемещённых, изменённых и дублирующихся функций;
- сводка рисков и итоговое заключение с доказательствами;
- журнал работы аналитика, контролёра и ограниченного цикла исправления;
- проверка существования источника и дословного вхождения каждой цитаты.

## Архитектура

```text
Документы «до» + «после»
          │
          ▼
 Извлечение текста и пунктов
          │
          ▼
 Агент-аналитик ──► нормализация функций
          │         семантическое сопоставление
          │         классификация изменений
          ▼
 Агент-контролёр ─► проверка ссылок и полноты
          │
          ▼
 Заключение + таблица отклонений + источники
```

Оркестратор извлекает текстовые фрагменты и передаёт оба комплекта целиком аналитику.
Выделение и сопоставление функций выполняются в одном структурированном вызове LLM.
Перед модельным контролёром код проверяет ссылки и дословные цитаты. Контролёр получает
исходники, результат и ошибки проверки; по замечаниям запускается ограниченное
исправление (по умолчанию одно). При выборе версии ошибки источников имеют приоритет
перед модельной оценкой. Итоговое заключение собирается из принятых находок и
предупреждений, без отдельной генерации новых утверждений. В интерфейсе
видны этапы анализа, уровень риска, пары сопоставленных пунктов и фрагменты-основания.

## Быстрый запуск

### Требования

- Docker Engine 24+
- Docker Compose v2
- API-ключ выбранного LLM-провайдера

### 1. Настройка окружения

```bash
cp .env.example .env
cp .back_env.example .back_env
cp .front_env.example .front_env
```

Заполните значения в локальных env-файлах. Секреты не должны попадать в Git.

### 2. Запуск

```bash
docker compose up --build
```

После запуска:

- приложение: <http://localhost:3001>
- Swagger UI: <http://localhost:8010/docs>
- проверка backend: <http://localhost:8010/health>

Compose запускает три сервиса: production-сборку frontend на nginx, FastAPI backend
и PostgreSQL с расширением pgvector. Запуск в фоне: `docker compose up --build -d`.
Статус сервисов: `docker compose ps`, общие логи: `docker compose logs -f`.

Остановка: `docker compose down`. Удаление локальных данных БД: `docker compose down -v`.

## Локальная разработка

Backend: из `backend/` установите `pip install -e '.[dev]'`, задайте `OPENAI_API_KEY`
в окружении и запустите `uvicorn app.main:app --reload --port 8010`.
Frontend: из `frontend/` выполните `npm ci && npm run dev`.
Docker Compose остаётся эталонным способом запуска решения для жюри.

Тесты backend (из `backend/`): `python -m pytest -q`. Они проверяют парсинг,
валидацию цитат, ограниченное исправление, формирование заключения и путь
загрузка → результат через API. В тестах модель заменена заглушкой: это проверки
логики, а не измерение качества модели на документах заказчика.

Frontend собирается двухстадийным Dockerfile: Node используется только на стадии сборки, а готовая SPA раздаётся через nginx. Адрес API передаётся при старте контейнера через `API_BASE`, поэтому один образ работает в разных окружениях без пересборки.

1. Откройте приложение, загрузите редакции ДО и ПОСЛЕ и запустите реальный анализ.
2. Покажите сводку и отклонение, откройте цитаты и сравните их с оригиналами.

## Ограничения и дальнейшее развитие

- Нет RAG, embeddings и tool calling со стороны LLM: используется полный текстовый
  контекст и явная оркестрация в Python. Для больших комплектов нужна пакетная обработка.
- DOCX: читаются обычные абзацы и строки таблиц в порядке документа. Автонумерация
  адресуется как «абзац N», а не восстановленный номер Word. Повторяющиеся номера
  получают метки фрагментов. Колонтитулы, текстовые поля, вложенные таблицы и схемы
  не покрыты полностью. OCR и надёжное распознавание графических оргструктур отсутствуют.
- Точное совпадение цитаты не гарантирует правильной интерпретации. Оценка контролёра
  субъективна; полнота обнаружения потерь и число ложных срабатываний не измерены.
  Число функций ДО/ПОСЛЕ — оценка LLM; `unchanged` считает только явно сопоставленные пары,
  а не все реально сохранённые функции. Полного реестра покрытия пока нет.
- Дублирование в одной редакции и конфликт интересов ещё требуют отдельной модели
  доказательств; текущая схема findings рассчитана на одну ссылку ДО и одну ПОСЛЕ.
- Результаты теряются при рестарте backend. Прогресс приблизительный, подробный журнал
  появляется после завершения. Нет авторизации, постоянной истории и очереди заданий.
- Текст загруженных документов передаётся OpenAI. Для реальных корпоративных данных
  необходим согласованный заказчиком режим обработки; используйте обезличенные примеры.

Приоритеты развития: полный реестр функций и покрытия, несколько доказательств на
вывод, эталонный набор оценок заказчика, постоянное хранение и восстановление заданий.
