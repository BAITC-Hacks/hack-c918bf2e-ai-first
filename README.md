# AI First

> ИИ-аудитор организационных изменений команды **AI First** для хакатона **hackalem.ai 2026**.

## О проекте

Проект разрабатывается в специальном треке **«Казахтелеком»** и решает задачу
**«Анализ организационной структуры и функционала»**.

При реорганизации положения о подразделениях и организационные структуры обычно
сверяют вручную. Из-за объёма документов отдельные функции могут потеряться,
задублироваться или незаметно перейти между подразделениями. AI First сравнивает
комплекты документов «до» и «после», классифицирует изменения и формирует
проверяемое заключение со ссылками на конкретные пункты исходных документов.

**Ценность:** специалист получает предварительную карту рисков реорганизации и
ссылки для проверки. Экономия времени пока не измерена на работе реального заказчика.

## MVP (в разработке)

- загрузка двух комплектов документов: «до» и «после» реорганизации;
- извлечение подразделений, функций и ссылок на пункты документов;
- сопоставление семантически эквивалентных функций;
- выявление потерянных, добавленных, перемещённых, изменённых и дублирующихся функций;
- отдельный блок потенциальных конфликтов интересов и дублирования внутри редакции
  с несколькими проверяемыми источниками в интерфейсе и заключении;
- сводка рисков и итоговое заключение с доказательствами;
- журнал работы аналитика, контролёра и ограниченного цикла исправления;
- промежуточные итоги агентов и реестр доступны во время анализа и сохраняются в БД;
- проверка существования источника и дословного вхождения каждой цитаты.
- реестр извлечённых функций ДО → ПОСЛЕ с цитатами и незакрытыми сопоставлениями;
- учёт каждого текстового фрагмента: функции, нефункциональный текст или требует проверки.
- сохранение результатов, реестра и этапов в PostgreSQL; ссылки работают после рестарта.

## Архитектура

```text
Документы «до» + «после»
          │
          ▼
 Извлечение текста и пунктов
          │
          ▼
 Извлекатель функций ──► пакетная обработка всех фрагментов
          │              реестр обязанностей + незакрытые источники
          ▼
 Сопоставитель ───► пакеты ID функций ДО → ПОСЛЕ
          │
          ▼
 Агент-аналитик ──► отклонения и изменения структуры по исходникам
          ▼
 Агент-контролёр ─► проверка ссылок и полноты
          │
          ▼
 Заключение + таблица отклонений + источники
```

Оркестратор извлекает текстовые фрагменты. Отдельный LLM-извлекатель рассматривает
их пакетами, возвращая решение для каждого фрагмента и обязанности с цитатами.
Пропущенный ответ, ошибка API или неподтверждённая цитата оставляют источник в
статусе «требует проверки». Отдельный сопоставитель работает пакетами функций ДО;
каждый пакет видит весь компактный реестр действий ПОСЛЕ. Несопоставленные функции
ПОСЛЕ проходят обратную проверку на новизну. Аналитик отдельно ищет отклонения в
полных исходниках, а контролёр получает исходники, находки и сопоставленный реестр.
Каждая функция ДО получает запись сопоставления; пропуск не превращается в потерю.
Несопоставленные функции ПОСЛЕ также остаются видимыми. Неполное извлечение противоположного
комплекта блокирует окончательный статус lost/added в реестре, заменяя его needs_review.
Перед модельным контролёром код проверяет ссылки и дословные цитаты. Контролёр получает
исходники, результат и ошибки проверки; по замечаниям запускается ограниченное
исправление (по умолчанию одно). При выборе версии ошибки источников имеют приоритет
перед модельной оценкой. Итоговое заключение собирается из принятых находок и
предупреждений, без отдельной генерации новых утверждений. В интерфейсе
видны этапы анализа, уровень риска, пары сопоставленных пунктов и фрагменты-основания.

## Быстрый запуск

### Требования

- Docker Engine 24+
- Docker Compose v2
- API-ключ выбранного LLM-провайдера

### 1. Настройка окружения

```bash
cp .env.example .env
cp .back_env.example .back_env
cp .front_env.example .front_env
```

Заполните значения в локальных env-файлах. Секреты не должны попадать в Git.

В `.back_env` обязателен `OPENAI_API_KEY`; модель задаётся `OPENAI_MODEL`.
`AGENT_MAX_REVISIONS` — число исправлений отчёта (0–2, по умолчанию 1).
Извлечение ограничено `REGISTRY_BATCH_SIZE` (35 фрагментов), `REGISTRY_WORKERS`
(3 параллельных запроса) и `REGISTRY_MAX_BATCHES` (40 пакетов на оба комплекта).
Сопоставление использует `REGISTRY_MATCH_BATCH_SIZE` (20 функций); лимит 40 пакетов
применяется отдельно к извлечению и отдельно к прямой/обратной сверке суммарно.
Источники сверх лимита не исчезают: показываются как требующие проверки.
Каждый запрос извлечения/сопоставления имеет timeout 90 секунд и не более одного повтора.
Исправление отчёта сохраняет реестр; незакрытые сопоставления не маскируются.

### 2. Запуск

```bash
docker compose up --build
```

После запуска:

- приложение: <http://localhost:3001>
- Swagger UI: <http://localhost:8010/docs>
- проверка backend: <http://localhost:8010/health>

Compose запускает три сервиса: production-сборку frontend на nginx, FastAPI backend
и PostgreSQL (образ с pgvector, векторный поиск не используется). Запуск в фоне: `docker compose up --build -d`.
Статус сервисов: `docker compose ps`, общие логи: `docker compose logs -f`.

Таблица результатов создаётся автоматически. Compose передаёт `DATABASE_URL` из
настроек БД в `.env`; ручных изменений схемы не требуется. `/health` проверяет БД.
Результаты и файлы находятся в именованных томах: обычный `docker compose down`
их сохраняет. **`docker compose down -v` удаляет тома БД и загруженных документов.**

Готовый анализ после рестарта доступен по прежней ссылке. Запуск, прерванный остановкой,
получает `failed / ANALYSIS_INTERRUPTED` с последним сохранённым этапом. Автоматического
продолжения и повторных платных запросов нет: для нового запуска загрузите документы
снова. Поддерживается **один процесс backend**; второй отклоняется блокировкой в БД.

## Локальная разработка

Backend: из `backend/` установите `pip install -e '.[dev]'`, задайте `OPENAI_API_KEY`
и `DATABASE_URL` доступной PostgreSQL в окружении и запустите
`uvicorn app.main:app --reload --port 8010`. БД в Compose наружу не опубликована;
для стандартного запуска используйте backend внутри Compose. Вне Docker нужна
собственная доступная БД. Вариант хранения в памяти используется только в тестах.
Frontend: из `frontend/` выполните `npm ci && npm run dev`.
Docker Compose остаётся эталонным способом запуска решения для жюри.

Тесты backend (из `backend/`): `python -m pytest -q`. Они проверяют парсинг,
валидацию цитат, ограниченное исправление, формирование заключения и путь
загрузка → результат через API. В тестах модель заменена заглушкой: это проверки
логики, а не измерение качества модели на документах заказчика.

Проверки реальной PostgreSQL включаются переменной `TEST_DATABASE_URL`: они создают
и удаляют только собственные временные схемы, не затрагивая сохранённые анализы.
Проверяются повторное открытие хранилища, перезапуск API, прерванные запуски,
изоляция снимков и защита от второго backend-процесса.

Проверка с реальной моделью (тратит API-кредиты, отправляет только синтетические
документы): из `backend/` выполните `python scripts/live_registry_smoke.py` при
запущенном API. Ожидаются пять исходов: сохранение при перенумерации, изменение,
передача, потенциальная потеря и новая функция. Это небольшой smoke-test,
а не репрезентативная оценка качества на корпоративных документах.

Регрессионные проверки frontend: из `frontend/` после `npm ci` выполните `npm test`.
31 сценарий в 6 тестовых файлах проверяет заключение, охват, фильтры реестра,
источники, структурные риски, разделение демо/реального анализа и повторные запуски.
Пустой список потерь не должен превращаться в утверждение о полном распределении функций.
Для проверки TypeScript и production-сборки выполните `npm run build`.

Отдельный opt-in тест структурных рисков: из `backend/` выполните
`python scripts/live_structural_risk_smoke.py`. Он расходует API-кредиты и использует
только синтетические документы: самопроверка закупок, дублирование отчётности и
отрицательный контроль (независимая проверка другим отделом в редакции ДО).

Результаты контрольных прогонов и границы их интерпретации:
[`docs/VALIDATION.md`](docs/VALIDATION.md).

Frontend собирается двухстадийным Dockerfile: Node используется только на стадии сборки, а готовая SPA раздаётся через nginx. Адрес API передаётся при старте контейнера через `API_BASE`, поэтому один образ работает в разных окружениях без пересборки.

## Демонстрация

1. Откройте приложение, загрузите редакции ДО и ПОСЛЕ и запустите реальный анализ.
2. Покажите сводку и отклонение, откройте цитаты и сравните их с оригиналами.
3. Откройте реестр функций: найдите соответствия ДО → ПОСЛЕ и включите фильтр
   «Только требует проверки». Разверните решения по исходным фрагментам.
4. Покажите отдельный блок рисков внутри редакции и все цитаты, на которых основан риск.
5. Покажите журнал проверки/исправлений, ограничения и предварительное заключение.

Демонстрационные данные frontend — отдельный mock-режим, не результат анализа файлов.

## Ограничения и дальнейшее развитие

- Нет RAG, embeddings и tool calling со стороны LLM: используется полный текстовый
  контекст и явная оркестрация в Python. Извлечение и сопоставление функций пакетные,
  но аналитик отчёта и контролёр пока получают полный текст. Большие комплекты требуют
  нескольких минут и заметно больше API-запросов; время и расход нужно измерять на данных.
- DOCX: читаются обычные абзацы и строки таблиц в порядке документа. Автонумерация
  адресуется как «абзац N», а не восстановленный номер Word. Повторяющиеся номера
  получают метки фрагментов. Колонтитулы, текстовые поля, вложенные таблицы и схемы
  не покрыты полностью. OCR и надёжное распознавание графических оргструктур отсутствуют.
- Точное совпадение цитаты не гарантирует правильной интерпретации. Оценка контролёра
  субъективна; полнота обнаружения потерь и число ложных срабатываний не измерены.
  Число функций ДО/ПОСЛЕ — число записей реестра с проверенными цитатами, не оценочный
  скаляр LLM. Повторные упоминания обязанности в разных фрагментах могут учитываться
  отдельно. Рассмотрение 100% фрагментов не доказывает, что модель извлекла все функции:
  даже решение «нефункциональный текст» может быть неверным. Статусы сопоставления
  являются модельными выводами и требуют экспертной проверки.
- Backend возвращает отдельные `structural_risks` с 2–6 источниками одной редакции.
  Нужны минимум два разных фрагмента; один пункт с обеими обязанностями пока не
  принимается как достаточная пара доказательств. Подтверждение цитат не доказывает
  конфликт: смысл оценивается моделью и требует проверки специалистом. Интерфейс
  показывает риски отдельно от отклонений ДО → ПОСЛЕ, не добавляя их к прежним счётчикам.
  В старых анализах без этого поля показывается неизвестный результат, а не отсутствие рисков.
- Результаты и этапы сохраняются в PostgreSQL. Нет автоматического продолжения прерванного
  анализа, распределённой очереди и поддержки нескольких backend-процессов.
  Этапы прогресса отражают фактические операции,
  но проценты условные, не оценка оставшегося времени. Журнал обновляется после реальных
  шагов; реестр сохраняется после извлечения и сопоставления, не после каждого пакета.
  Нет авторизации и экрана списка ранее выполненных анализов;
  сохранённые результаты открываются по ссылке с ID.
- Текст загруженных документов передаётся OpenAI. Для реальных корпоративных данных
  необходим согласованный заказчиком режим обработки; используйте обезличенные примеры.

Приоритеты развития: экспертная оценка полноты реестра, эталонный набор оценок заказчика,
возобновление заданий и история в интерфейсе.
