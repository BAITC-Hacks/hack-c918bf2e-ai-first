# 0004 — Несколько доказательств для рисков внутри редакции

## Проблема

Одна ссылка ДО и одна ПОСЛЕ подходят для изменения функции, но не доказывают
дублирование внутри новой структуры. Смена подписи источника в UI не меняет его
принадлежность. Дублирование также не тождественно конфликту интересов.

## Решение

Добавочное поле `Analysis.structural_risks`: отдельные kind `duplicate` и
`conflict_interest`. Каждый риск имеет severity, пояснение, рекомендацию и 2–6
явно размеченных источников `{side, evidence}`. Старые Finding и summary сохранены,
summary считает только findings. Для старых/незавершённых результатов поле null.

Аналитик возвращает риски в том же структурированном ответе, без дополнительного
LLM-запроса. Они проходят общую проверку и ограниченный цикл исправления с критиком.
Перед критиком и перед публикацией проверяются:

1. Точное соответствие каждого документа и однозначного локатора.
2. Непрерывное дословное вхождение каждой цитаты в свой источник.
3. Принадлежность всех доказательств одному комплекту — ДО либо ПОСЛЕ.
4. Как минимум два разных локатора, а не две копии одной цитаты.
5. Отсутствие повторных рисков того же kind с тем же набором оснований.

Новые findings с type=duplicate и только парой ДО/ПОСЛЕ исключаются. Старые
сохранённые записи доступны без переинтерпретации сторон. Финальное backend-заключение
содержит только принятые риски и все их ссылки. У frontend отдельный handoff;
для рисков нужны отдельные карточки и включение в копируемое заключение.

## Ограничения

Это потенциальный риск для специалиста, не юридическое заключение. Простое правило
о раскрытии конфликта, общий и детальный раздел одной функции, исполнение и независимый
контроль разными отделами не должны автоматически становиться риском. Эти смысловые
различия проверяет модель, а не детерминированный код. Один пункт, в котором уже
совмещены обе обязанности, не проходит консервативное правило двух локаторов.
Полнота обнаружения не измерена на размеченном корпусе.

Формат списков, вложенных объектов и nullable-полей сверён с
[официальной документацией Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).
Используется существующий Responses/Pydantic-адаптер; модель не менялась.
